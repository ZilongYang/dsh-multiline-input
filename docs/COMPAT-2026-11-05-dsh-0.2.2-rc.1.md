## 三、逐项核查：composer 契约（核心）

### 3.1 ✅ `phase` 新增 `'sending'`，语义正是插件预期

0.2.1-rc.5 的 phase 只有 `'plain' | 'adjudicating' | 'claimed' | 'submitting'`；0.2.2 新增 `'sending'`：

```ts
readonly phase: 'plain' | 'adjudicating' | 'claimed' | 'submitting' | 'sending'
```

对应 release note 的「消息在宿主确认接收后才显示并清空草稿；发送期间输入框只读」。

状态机实际行为（`input/machine.ts`）：

```
enter → phase='sending'（草稿冻结、编辑器只读）
      → 宿主接受 → commit-draft 清空 + pendingSubmissions 增长 → phase='plain'
      → 拒绝/失败 → phase='plain'，草稿保留（不清空）
```

**插件的双路径设计正好覆盖**（0.2.1 的 `client.js`：`sendingSeenRef` 在 `991-992`，捕获 effect 在 `1029-1058`）：

- `sendingSeenRef` 用"是否见过 `sending`"做版本嗅探
- 见过 → 走新分支：`sending` 期间从冻结的 `draft` 捕获文本，`pendingSubmissions` 增长时提交
- 没见过 → 走 rc.5 的乐观回显分支
- `advanceCapture()` 里"接受优先"的判断顺序，正好覆盖"接受与下一次 `sending` 落在同一次渲染"的边界

**结论：历史记录功能在 0.2.2 上不会丢，且会走更准确的路径。**

补充：0.2.2 的 `InputEvent.enter` 现在携带 `occurrences` / `quotes` / `attachmentIds`，`sink-settled` 取代了 detached 发送；这些都是宿主内部改动，插件只读 `phase` / `draft` / `pendingSubmissions`，不需要跟随。

### 3.2 ✅ `pendingSubmissions` 字段未变

```ts
export interface PendingSubmission {
  readonly requestId: SessionRequestId
  readonly placement: PendingSubmissionPlacement
  readonly time: number

```

`SessionSnapshot.pendingSubmissions` 两版本逐字相同。插件用 `requestId` 做差集判"新增即接受"、读 `item.text`，**继续有效**。

`PendingSubmission.text` 的注释是"Prompt text exactly as it will be sent（一个文本块）"——带引用时它就是含 Markdown 块引用的整段文本，与 `draft` 一致。

### 3.6 ⚠️ 真回归：`sending` 期间多行高度塌陷（0.2.1 已修）

这一项是复核时补上的——契约没变，但 DOM 的**可编辑性**变了，样式选择器依赖了它。

| 环节 | 0.2.2 的事实 |
|---|---|
| 相位 | `InputBar.tsx`：`machineBusy` 含 `'sending'`（第 161 行），`editable = live && !locked && !machineBusy`（第 170 行） |
| DOM | `ComposerContentEditable.tsx`：`contentEditable={editor !== null && editable}` → 发送期间渲染 `contenteditable="false"` |
| 宿主高度 | `InputBar.module.css`：`.input { min-height: 36px }`（`.hero .input` 52px） |
| 0.2.0 插件规则 | `[data-composer-input][contenteditable="true"] { min-height: calc(4 * 1lh + 8px) }`（主规则 + `@supports` 回退各一处） |

→ 每次普通消息发送，多行 composer 先塌回 36px（约 1 行），Host 接受、相位回 `plain` 后再弹回 4 行。rc.5 不出现，因为 rc.5 的普通发送是 detached 的、相位始终 `plain`。

**0.2.1 的修法**：

```js
const FLOOR_SELECTOR = `html[${MODE_ATTRIBUTE}="multi"] [data-composer-card] [data-composer-input]:is([contenteditable="true"], [data-phase]:not([data-phase="plain"]))`
```

- 只读提交相位（`sending` / `adjudicating` / `submitting` / `claimed`）同样保持 4 行；
- 无 Session 的 Workspace picker 是 `data-phase="plain"`（或无该属性），不被匹配；
- 回归测试断言主规则与 `@supports` 回退都用了新选择器，且旧的 `[contenteditable="true"]` 专属选择器已消失。

**教训**：`contenteditable` / `data-phase` 和 `data-*` 锚点一样是契约，任何"只在可编辑时生效"的样式都要显式覆盖只读相位。

## 五、引用（quote）对历史记录的真实影响（修正版）

0.2.2 新增「把聊天文本作为引用插入输入框」功能。**这里原先的结论（"草稿字符串可能不含引用原文"）是错的**，按源码更正如下：

| 事实 | 证据 |
|---|---|
| 引用是 Lexical 的独立节点（`QuoteNode`），但它的剪贴板投影**计入草稿字符串** | `QuoteNode.getTextContent()` 返回 `formatQuoteText(text)`（Markdown 块引用）；`input/editor/projection.ts` 把它累加进 `clipboardText`，即 `InputState.draft` |
| 提交时引用另有结构化字段 | `SubmitAttempt` / `InputEvent.enter` 增 `quotes: readonly DraftQuote[]`（偏移 + 长度 + 原文） |
| `setDraft(text)` 只写纯文本 | `facade.setDraft(text)` 在无 references / quotes 时走 `draftEditor.setDraft(text)`，整篇替换 → 引用 chip 被清掉 |

**对本插件的真实影响：**

1. 带引用发送时，历史里记录的是**含 `> 引用原文` 的完整文本**——内容不会丢。
2. `↑` 召回走 `inputActions.setDraft(纯文本)`，引用 chip 不会被复原，`>` 行以普通文本写回。这是"历史召回 = 纯文本草稿"的既有语义，**不需要适配**，写进 README 已知限制即可。
3. 宿主的公开写入口（`InputActions.setDraft(text: string)`）只接受字符串，插件拿不到 `quotes` 通过 slot props 的读取面；要做结构化召回必须等宿主扩展契约。

**0.2.1 的处理**：不改代码，README「已知限制」注明引用降级行为；历史记录本身不做前缀剥离（保留原文）。
